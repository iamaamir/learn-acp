Sessions: Where State Lives

Promise: you will answer “if the Client crashes, does the Agent remember?” — precisely.

Framing: the bar tab

Last time we left a question: where does multi-turn memory live? Here’s the answer device: a session is a bar tab. session/new opens the tab (tab number = sessionId). Each session/prompt orders another round — the bartender (Agent) remembers everything on your tab. The receipt streams back as session/update notifications.

Memorable label: “The Tab” — the Agent keeps the tab, the Client keeps the tab number. Lose the number, lose the tab.

    import { SessionStore } from './src/acp-session.mjs';
const s = new SessionStore();
const id = s.open('/proj');       // session/new
s.prompt(id, 'fix login');        // prompt #1

Payoff

Interview Q: “Where does multi-turn state live in ACP?”

Model answer: “The Agent owns conversation history and context, keyed by the sessionId minted in session/new. The Client owns the handle — the id, the cwd, the UI. Each session/prompt carries id + new content only; the Agent joins it to stored history. In v2 the Agent acks immediately and streams everything else via session/update. So a Client crash with a saved id resumes cleanly; without it, you must open a new tab — history is unreachable.”

Pro tip (production): persist {sessionId, cwd} together on every prompt, and never reuse a sessionId after changing cwd — the Agent’s file context is scoped to the directory from session/new. Stale id + new directory = edits grounded in the wrong tree.

With this, you can now build: a crash-safe client loop — open once, save the id, prompt in a loop, resume on restart.
